# Contributing

## Layout

- `crates/` — the Rust workspace; `crates/suspect-cli` builds the `suspect`
  binary (CLI and `suspect lsp`).
- `editors/vscode`, `editors/zed` — editor clients for `suspect lsp`;
  `editors/multiclient` holds Neovim/Zed smoke scripts.
- `rules-runtime/` — the TypeScript SDK and Bun worker for custom rules.
- `xtask/` — `cargo xtask ci`, corpus fetching and SDK verification tasks.
- `docs/` — see [docs/README.md](docs/README.md) for the index.

## Checks

`cargo xtask ci` runs every job CI runs, with the same commands; `cargo xtask
ci --list` shows them, `cargo xtask ci clippy test` runs a subset, and a CI
failure names the job to rerun locally. Jobs whose tool is missing fail with
an install hint; `--skip-missing` reports them as skipped instead.

`cargo xtask ci fmt clippy test` is the quick loop. The full run includes
`bench-smoke`, `corpus-validation` (downloads real-world specs),
`platform-smoke`, the editor extensions, `rules-runtime` and `links` (lychee
0.24.2, offline; see `lychee.toml`). `rust-toolchain.toml` pins the Rust
version CI uses.

The real-host VS Code smoke needs a desktop session and stays manual (macOS
app path by default, `SUSPECT_VSCODE_BIN` overrides it):

```sh
cargo build -p suspect-cli && (cd editors/vscode && npm run test:host:smoke)
```

## Generated files

- `docs/CLI.md` is rendered from the clap command tree. After changing a
  command or flag, regenerate it:
  `SUSPECT_BLESS=1 cargo test -p suspect-cli --test cli_reference`.
  `cargo xtask bless` regenerates every generated doc (`docs/CLI.md`,
  `docs/SDK-FEATURES.md`) in one step.
- `editors/vscode/dist` and `node_modules` are build output and are not
  committed.

## Native SDK gates

Tests that compile and run generated SDKs need real toolchains (Go, JDK/Maven,
.NET, Swift, Dart, Node, Ruby, PHP, Python). The rule:

- A test in the default suite may skip when a tool is missing. It prints one
  `skipped:` line naming the tool and how to install it.
- A test marked `#[ignore]` is an explicit gate. When you run it
  (`cargo test -p suspect-codegen -- --ignored`), a missing tool or input
  fails it. No gate passes by skipping.
- CI sets `SUSPECT_REQUIRE_TOOLS` for the tools it installs, so a skip there
  is a failure.

Use `suspect_codegen::toolchain::optional` in default-suite tests and
`toolchain::require` in `#[ignore]` gates; `toolchain.rs` declares each tool,
its minimum version and its `SUSPECT_*_BIN` override. Gates that read the
OpenRouter specification need `OPENROUTER_WEB_ROOT=/path/to/openrouter-web`
and get it from `suspect_codegen::test_inputs`.

The corpus suite skips without `corpus/` (`cargo xtask fetch-corpus`), unless
`SUSPECT_REQUIRE_CORPUS=1`, which `cargo xtask ci corpus-validation` sets.

## Releasing

One version covers the binary, the LSP, both editor extensions and the rules
SDK; the tag is `v<version>`. Before 1.0, a release that removes or renames a
command, flag, config key or exit code bumps the minor version; anything else
bumps the patch.

1. **Bump PR.** `cargo xtask bump 0.2.0` sets every version line (crates,
   both lockfiles, `editors/vscode`, `editors/zed`, `rules-runtime`) and, with
   [git-cliff](https://git-cliff.org) installed, prepends the `0.2.0` section
   to `CHANGELOG.md` from the conventional commits since the last tag
   (`cliff.toml`). Edit the section into readable release notes, then open
   the PR. `cargo xtask check-versions` (CI job `check-versions`) keeps the
   lines in step. For `0.1.0` there is no bump: set the date on the
   hand-written `CHANGELOG.md` entry instead.
2. **Tag.** After the PR merges, tag the merge commit on `main` and push the
   tag: `git tag v0.2.0 && git push origin v0.2.0`. A tag with a pre-release
   suffix (`v0.2.0-rc.1`) builds everything and creates a pre-release, but
   skips Homebrew and the editor registries.
3. **What `.github/workflows/release.yml` does** (generated by
   [cargo-dist](https://opensource.axo.dev/cargo-dist/) from
   `dist-workspace.toml`):
   - builds `suspect` for the seven targets in `dist-workspace.toml` and
     packs `suspect-cli-<target>.tar.gz` (`.zip` on Windows) with a `.sha256`
     each, the licences, `README.md`, `CHANGELOG.md` and
     `THIRD-PARTY-NOTICES.md`, plus GitHub attestations;
   - builds the shell and PowerShell installers and the Homebrew formula;
   - runs `package-editors.yml`: checks every version line against the tag,
     builds, tests and packages `suspect-vscode-<version>.vsix`, installs it
     into a headless VS Code, smoke-tests the Linux (musl), macOS and Windows
     archives and checks every asset name;
   - creates the GitHub release with the `CHANGELOG.md` section as its body;
   - pushes `suspect.rb` to `LukasParke/homebrew-tap`;
   - runs `publish-editors.yml`: the `.vsix` to the VS Code Marketplace and
     Open VSX, and a PR to `zed-industries/extensions` that moves the
     `suspect` submodule to the tag.

   On pull requests the workflow only runs `dist plan`. Never edit
   `release.yml` by hand: change `dist-workspace.toml` and run `dist
   generate` (the CI job `dist-check` fails when they drift). Upgrading dist
   is `dist init` with the new version, in its own PR.
4. **After the release.** Run the `action-smoke` workflow (Actions tab,
   manual) with the new version to check the GitHub Action, and move its
   default version forward.

`THIRD-PARTY-NOTICES.md` is generated; after a dependency change run
`cargo about generate --locked -m crates/suspect-cli/Cargo.toml -o
THIRD-PARTY-NOTICES.md about.hbs` (cargo-about with `--features cli`).

### Manual prerequisites

The workflows cannot create these; set them up once before the first tag.
Every publish step that lacks its secret prints a notice and skips, so a
release without them still produces the GitHub release.

- **Homebrew tap**: create the public repository `LukasParke/homebrew-tap`
  and a fine-grained token with contents write on it, stored as the
  `HOMEBREW_TAP_TOKEN` secret. Without it the `publish-homebrew-formula` job
  fails (it is dist's job and has no skip).
- **GitHub environment** `release` with required reviewers. The editor
  publish jobs run in it; store their secrets there, not as repository
  secrets.
- **VS Code Marketplace**: the publisher `suspect` (or change `publisher` in
  `editors/vscode/package.json` before the first publish if the id is
  taken) and an Azure DevOps token scoped to Marketplace (Manage), stored as
  `VSCE_PAT`.
- **Open VSX**: an account, the `suspect` namespace (`npx ovsx
  create-namespace suspect`) and an access token, stored as `OVSX_PAT`.
- **Zed registry**: the first submission is a manual PR to
  `zed-industries/extensions` adding this repository as a submodule with
  `path = "editors/zed"` (see Zed's publishing guide). Once it is merged,
  create a fork of that repository, set the repository variable
  `ZED_REGISTRY_FORK` to its `owner/name`, and store a token that can push
  to the fork and open PRs as `ZED_EXTENSIONS_TOKEN`.

## Conventions

- Exit codes: `0` clean, `1` findings or failed checks, `2` usage or
  environment error, `130` interrupted. Long-running servers (`gateway`,
  `lsp`, `watch`, `bridge`, `codegen-session --watch`) exit `0` on Ctrl-C.
  Commands return `suspect_cli::Exit`; `std::process::exit` is banned by
  `crates/suspect-cli/clippy.toml`, and `exit::abort` is the one immediate
  exit. Ctrl-C goes through `suspect_cli::interrupt`: call
  `interrupt::graceful()` to drain, never `tokio::signal::ctrl_c`.
- Settings belong in `crates/suspect-config` so the CLI and the language
  server read them the same way.
