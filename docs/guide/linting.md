# Checking and linting

`suspect check` runs every check the editor runs, over one or more documents,
and exits `1` when an error-severity finding remains. `suspect validate` and
`suspect lint` are the same pass with a filter. Every flag is listed in the
[command reference](../reference/cli.md#suspect-check).

```console
$ suspect check api.yaml                      # every check; exit 1 on errors
$ suspect check api.yaml --only lint,markdown # some checks
$ suspect check api.yaml --parse-only         # syntax and $ref resolution only
$ suspect validate api.yaml                   # structure and semantics
$ suspect lint api.yaml                       # lint, markdown and TypeScript rules
```

The checks are `syntax`, `ref`, `validate`, `swagger`, `arazzo`, `overlay`,
`load-profile`, `config`, `extension`, `lint`, `markdown`, `rules` and
`admission`. A document is checked by the ones that apply to its kind
(OpenAPI, Swagger 2.0, Arazzo, Overlay, a load profile or a suspect config
file).

## Findings

Each finding has one code, one severity and a location:

```text
api.yaml:8:7 [WARNING] oas-operation-missing-operationId: get operation is missing an operationId
how to fix: Add an `operationId` so generated SDK methods carry a stable name.
```

A problem is reported once, under one code, in the CLI, CI, SARIF and the
editor. Every code, with its check, default severity and aliases, is in the
[diagnostic codes reference](../reference/diagnostics.md). Some lint rules have older Spectral names (`operation-operationId`);
they are aliases of the canonical code, and both spellings work in
configuration and suppressions.

`--format` selects the output: `text` (default), `json` (the findings and the
suppressed ones), `sarif` (for code scanning) or `junit`.

Exit status: `0` when no error-severity finding remains, `1` when one does,
`2` for a usage or environment error (an unreadable ruleset, a rejected
setting).

## SDK findings

The `sdk-*` readiness codes and SDK admission run only when the project
configures code generation (a `codegen:` section in `.suspect.yaml`, or
`codegen` targets in `suspect.project.json`). `--sdk` and `--no-sdk` override
that.

## Severity and rule settings

Settings live in `.suspect.yaml`, and the CLI, `suspect ci` and the editor
read the same file:

```yaml
lint:
  min_severity: warning       # hide findings below this floor
  design: info                # severity for design-class rules, or off
  rules:
    info-contact: error       # canonical code or alias -> severity
    oas-operation-no-error-response: off
  ruleset: rules/custom.yaml  # Spectral-compatible ruleset
  recommended: true           # the built-in rules
validate:
  strict_format: false        # assert JSON Schema `format` keywords
```

`lint.rules` merges per key across files (`extends`) and layers, so a project
file can override one rule without restating the others. Every key is in the
[configuration reference](../reference/config.md). Flags win over the
file: `--min-severity`, `--ruleset`, `--strict-format`. `suspect config
--explain` shows the value in effect for every key and where it came from.

## Suppressing a finding

A comment on its own line suppresses the listed codes for the next node (the
mapping pair or sequence item, with everything under it):

```yaml
paths:
  /pets:
    # suspect-disable-next-line oas-operation-missing-operationId -- generated by the gateway
    get:
      responses:
        "200": { description: ok }
```

- `# suspect-disable` is the short form of `# suspect-disable-next-line`.
  As a trailing comment (`get: # suspect-disable ...`) it applies to the node
  its own line starts.
- `# suspect-disable-file <code>...` anywhere in the document suppresses the
  codes for the whole document.
- `x-suspect-disable: [<code>, ...]` on a mapping works in YAML and JSON. It
  covers the mapping and the pair it is the value of.
- Text after `--` is a reason and is ignored.

`syntax-error` cannot be suppressed. An unknown code gives a
`suppression-unknown-code` warning. A suppression that matched nothing gives
`suppression-unused`, which is off until `lint.rules.suppression-unused` sets
a severity. Text output prints `N suppressed finding(s) hidden` on stderr;
`--format json` lists them under `suppressed`.

## Baselines

A baseline records today's findings so CI fails only on new ones:

```console
$ suspect check api.yaml --write-baseline .suspect-baseline.json   # exits 0
$ suspect check api.yaml --baseline .suspect-baseline.json
```

Or set it once for `check`, `validate`, `lint` and the `ci` check stage:

```yaml
check:
  baseline: .suspect-baseline.json
```

A finding is keyed by its canonical code, its document (relative to the
baseline file) and its JSON pointer, with a count per key. Messages and line
numbers are not part of the key, so rewording and moving code keep a finding
baselined. Renaming the path it sits under does not. A key's first `count`
findings are baselined, and any more are new. Text output prints `N
baselined finding(s) hidden`, JSON adds `"baselined": N`, and SARIF keeps
baselined results with `baselineState: "unchanged"` so code-scanning alerts
stay open. The editor ignores the baseline.

## Custom rules

Two kinds of custom rule are supported:

- **Rulesets.** A Spectral-compatible ruleset document (`lint.ruleset` or
  `--ruleset`) adds rules or redefines built-in ones.
- **TypeScript rules.** `suspect rules new <name>` scaffolds a rule file in
  `.suspect/rules/`. `suspect rules check <paths>` runs those files on
  [Bun](https://bun.sh). With `rules.enabled: true`, `check` and the editor
  run them too, from every directory in `rules.roots`:

  ```ts
  import { defineRule, r } from "@suspect/rules-sdk";

  export default defineRule({
    meta: { id: "operation-summary", description: "Operations have a summary" },
    given: r.operation,
    check(op, ctx) {
      if (!op.summary) ctx.report({ message: `${op.method} ${op.path} has no summary`, at: op });
    },
  });
  ```

  Without Bun, each document gets a `rules-runtime-unavailable` warning. A
  TypeScript rule id that clashes with a built-in code is a
  `rules-id-collision` error on the rule file. The runtime design is in
  [TS rule runtime](../design/ts-rule-runtime.md).

## In CI

`suspect ci` runs the same check stage for every project under a root, and
the GitHub Action runs `suspect check`:

```yaml
- uses: LukasParke/suspect/.github/actions/suspect@v0.1.0
  with:
    command: check
    paths: api.yaml
```

Upload `--format sarif` output to code scanning to see findings on pull
requests.
