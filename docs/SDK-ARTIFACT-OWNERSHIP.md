# Generated artifact ownership

The shared `suspect-artifact` writer now supports a version 1 ownership registry
at `.suspect-artifacts.json` inside the output root. Compiler generation and
template generation use it. This is file lifecycle tracking, not evidence that
the generated SDK implements its source contract correctly.

Each owner records a complete desired file set using normalized relative paths,
SHA-256 digests and byte lengths. The manifest is deterministic and contains no
timestamps or absolute checkout identity. Owners are stable logical names:
single-profile SDK commands use `suspect-sdk:<profile>`, sessions use their
configured owner, the library writer defaults to `suspect-codegen`, the
documentation preset uses `suspect-gen:preset:docs-md`, and custom CLI manifests
use `suspect-gen:custom`.
Use a distinct `--owner` for each custom generation stream sharing one root.
Changing an owner's desired file set makes its omitted files obsolete; another
owner's files are never adopted or removed.

The same preflight powers generation and drift checking. It reports missing,
changed, unchanged and obsolete output, edited/unowned conflicts, and missing
or stale ownership metadata. Invalid paths, symlinks, portable case/Unicode
collisions, duplicate manifest records, malformed metadata and unsupported
manifest versions block mutation. The manifest path is reserved. There is no
implicit version migration.

## Regeneration and user files

Missing desired files are created. Existing owned files can be regenerated when
they still match the last recorded bytes. An owned file already identical to
the current intended output can reconcile a stale manifest without rewriting
the file. Other edits are conflicts and block the whole preflighted batch.
Unrelated user files are left alone.

Obsolete files are removed only when this owner recorded them, their full bytes
still match the recorded digest and length, and they contain no retained user
content. Missing obsolete files cause only their ownership entries to be
retired. Edited obsolete files remain present with a conflict. Directories and
unrecorded temporary files are not cleaned up.

Template user-code regions have a separate `suspect-user-code-v1` managed-content
fingerprint. This excludes only the interiors of the documented marker pairs;
marker lines, line endings outside those interiors and surrounding generated
text remain managed. That fingerprint can authorize regeneration around edited
user code. It does not authorize deletion. The manifest separately records the
complete merged file bytes and whether nondefault user content has been retained
during this ownership entry's lifetime.
Files carrying that retained content remain protected when obsolete, even if
their full bytes have not changed since the last generation.

This protection persists across regeneration. A later template matching the
retained text, a user reverting the region to a default, or the same owner
using a frontend without region metadata does not release it. There is no
implicit release or force-delete switch. To deliberately retire such a file,
first move its user content somewhere safe and remove the file yourself, then
regenerate with that path omitted. The missing obsolete entry can then be
retired. If a still-desired path is recreated, its existing protection persists
until its ownership entry is retired.

Malformed markers and changes to the number of existing user-code regions
require an explicit content migration. Region matching remains positional;
changing their order without stable region identifiers is not a supported
migration mechanism.

## Explicit adoption of existing files

Output with no ownership record is preserved as a conflict, even if it matches
newly generated bytes. Identical content alone does not prove that a user file
belongs to the generator. To adopt reviewed, identical documentation output:

```sh
suspect gen api.yaml --preset docs-md --out site --adopt-identical
```

Only complete byte-identical files can be adopted. Different files and files
owned by another stream remain conflicts. Once adopted, an unedited file is
eligible for obsolete removal on later runs; adoption is an ownership change,
not a force-overwrite option. Keep the same owner on subsequent runs.
Adoption does not clear protection already recorded for an owned path. A
template adoption that retains nondefault user content records that protection
immediately and follows the retirement procedure above.

The library equivalents are `ArtifactBatch::with_ownership`,
`suspect_codegen::write_files_with_owner`, and
`suspect_gen::render_manifest_owned`, using `Adoption::Identical` explicitly.
Default APIs use `Adoption::Refuse`. `suspect_codegen::check_files` returns a
structured report; `matches_disk` is true only when output and metadata match.

`suspect gen --diff` writes nothing, including when the output directory does
not exist. It returns exit status 1 for generated/metadata drift or ownership
conflicts, and 0 when current. Invalid metadata or other operational failures
remain command errors. Diff output includes obsolete files and manifest drift.

## Interruption and concurrency limits

All changed files and the replacement manifest are staged before publication.
Generated files are replaced individually, eligible obsolete files are removed,
and the manifest is published last. Each replacement is atomic per file. The
batch is not a filesystem transaction, does not acquire a cross-process lock,
and does not provide compare-and-swap deletion. Content/path rechecks are best
effort; callers must avoid concurrent editors or generators in the same output
root. Directory durability across power loss is not claimed.

Interruption can leave partial new output with the previous manifest. A recorded
file matching the next requested output can reconcile its metadata; already
missing obsolete files can be retired. Newly created files absent from the
old manifest remain unowned and require explicit identical adoption. A damaged
or unsupported manifest is never silently replaced to make the run succeed.
Restore valid metadata or deliberately migrate reviewed output instead.

Focused tests exercise the public writer, compiler/template generation and real
CLI seams, including conflicts, obsolete removal, stale metadata, corruption,
symlinks, collisions and unchanged inode/mtime. The tracked OpenRouter repeated
generation check includes both generated output and ownership manifests.
