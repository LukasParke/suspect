# P5. One install and release path

Status: proposal. Depends on: P8 (should land first, so the version bump
and `publish = false` list are written once); P7 for the `CONTRIBUTING.md`
pointer only. Decided: the `LICENSE-MIT` copyright line stays "Luke Parke
and suspect contributors".

## Summary

A user installs `suspect` with one command (`curl | sh`, PowerShell, or
`brew install LukasParke/tap/suspect`), or the editor extension downloads
the same binary. Each `v*` tag builds binaries for seven targets, the
`.vsix`, checksums and installers in one workflow, publishes the VS Code
extension to Marketplace and Open VSX, updates the Homebrew tap, and opens
the Zed registry PR. In the code: [cargo-dist](https://opensource.axo.dev/cargo-dist/)
config in `dist-workspace.toml`, a generated `.github/workflows/release.yml`,
complete package metadata, `publish = false` on every crate outside a
seven-crate foundation set, one lockstep version bumped by `cargo xtask
bump`, and a `CHANGELOG.md` generated by git-cliff.

This is the toolchain's own release. It is unrelated to the user-facing
`suspect release-plan` / `release-publish` / `release-workflow` commands
(`crates/suspect-cli/src/lib.rs:483-493`), which plan releases of a user's
API from `release.json`.

## Problem

1. **No release workflow.** `.github/workflows/` holds `application-targets`,
   `ci`, `docs`, `native-evidence`, `platform` and `sdk-session-performance`.
   None triggers on tags, and the repository has no tags (`git tag` prints
   nothing). The only install path is `cargo install --path
   crates/suspect-cli` (`README.md:24`), which needs a Rust toolchain and a
   checkout.

2. **Every CI job runs on Linux.** All 20 `runs-on` entries across the six workflows are
   `ubuntu-latest`, `ubuntu-24.04` or a self-hosted Linux runner. macOS
   builds happen only on developer machines; Windows has never been built.

3. **Windows has known gaps.** `crates/suspect-cli/src/silence.rs:13-25`:
   `Silenced::start` is "a no-op on non-unix targets", so on Windows a
   `--format json|sarif` gate can print stage progress into the machine
   document. `crates/suspect-test/src/auth.rs:454,542` skip the credential
   file permission check outside unix. These are not build failures, but
   they are behaviour differences nobody has tested.

4. **The GitHub Action does not work outside this repository.**
   `.github/actions/suspect/action.yml:66` runs `cargo build --release -p
   suspect-cli` in a composite step, which runs in the caller's checkout.
   A repository that uses `LukasParke/suspect/.github/actions/suspect@...`
   has no `suspect-cli` package, so the step fails. No workflow in this
   repository uses the action either (`grep -rn actions/suspect .github`
   finds nothing).

5. **Package metadata is incomplete.** `Cargo.toml:5-10`
   (`[workspace.package]`) has `version`, `edition`, `rust-version`,
   `license`, `authors`, but no `repository`, `homepage` or `readme`. No crate
   has a `README.md`. `cargo package` prints "manifest has no documentation,
   homepage or repository" for each crate. cargo-dist's installers need
   `repository`. `editors/vscode/package.json` has no `license` or
   `repository`, no `@vscode/vsce` dev dependency and no `.vscodeignore`.
   `editors/zed/extension.toml` has no `repository` and `editors/zed/` has
   no licence file.

6. **The vendored YAML grammar ships without its licence.**
   `crates/suspect-syntax/grammars/json/LICENSE` exists;
   `crates/suspect-syntax/grammars/yaml/` holds only `src/` (`git ls-files
   crates/suspect-syntax/grammars`). The tree-sitter-yaml grammar is MIT and
   its notice must travel with binaries and crates.

7. **Only `xtask` sets `publish = false`.** (`xtask/Cargo.toml`; the short
   version said "no crate".) All 28 crates under `crates/` are publishable by
   default, but most cannot actually be published:
   - `cargo package` of the parse layer: `suspect-source`, `suspect-syntax`,
     `suspect-low`, `suspect-jsonpath` and `suspect-overlay` package and
     verify (`exit=0`, e.g. "suspect-syntax ... Packaged 29 files, 1.5MiB
     (131.6KiB compressed)").
   - `suspect-ref` fails: "no matching package named `suspect-ir` found ...
     required by package `suspect-ref`". The cause is a versioned dev
     dependency (`crates/suspect-ref/Cargo.toml:26`, `suspect-ir.workspace =
     true`, and the workspace entry carries `version = "0.1.0"`).
   - `suspect-gen`, `suspect-reverse` and `suspect-test` have path-only
     normal dependencies (`crates/suspect-gen/Cargo.toml:10`,
     `crates/suspect-reverse/Cargo.toml:9`,
     `crates/suspect-test/Cargo.toml:17-22`), which `cargo publish` rejects.
   - `suspect-rules` embeds `rules-runtime/src/*.ts` with
     `include_str!("../../../rules-runtime/src/worker.ts")`
     (`crates/suspect-rules/src/discover.rs:61-80`). Those files are outside
     the crate directory, so `cargo package -p suspect-rules --list` does not
     include them and the packaged crate would not compile. Because
     `suspect-cli` depends on `suspect-rules`, `cargo install suspect-cli`
     from crates.io is not possible without moving them.

8. **The short version's public list is not dependency-closed.** Publishing
   `suspect-lint` requires publishing everything it depends on:
   `suspect-ir` (used only by `crates/suspect-lint/src/quality.rs:9`), and
   through it `suspect-oas`, `suspect-overlay`, `suspect-ref`,
   `suspect-jsonpath`, `suspect-low`, `suspect-syntax`, `suspect-source`.
   `suspect-ir` describes itself as the model "shared by gen, test, gateway,
   and LSP" (`crates/suspect-ir/src/lib.rs:1-2`), an internal type.
   `suspect-lint` also exports `Finding` and `Severity`
   (`crates/suspect-lint/src/lib.rs:29-30`), which P1 replaces with
   `suspect-diag`.

9. **Versions live in many places.** The workspace version
   (`Cargo.toml:6`), 27 internal `version = "0.1.0"` entries
   (`Cargo.toml:15-42`), `editors/vscode/package.json:5`,
   `editors/zed/extension.toml:3`, `editors/zed/Cargo.toml:3`,
   `rules-runtime/package.json`, and the `@suspect/rules-sdk` shim written at
   run time (`crates/suspect-rules/src/discover.rs:110`,
   `"version":"0.1.0"`). The VS Code extension warns whenever its version is
   not exactly the server's (`editors/vscode/src/extension.ts:148`), so these
   must move together.

10. **No changelog.** No `CHANGELOG.md`. History is mostly conventional:
    199 of 216 non-merge commits match
    `^(feat|fix|docs|chore|test|style|perf|ci|refactor|build|revert)(scope)?!?: `.
    The 17 that do not are early milestone subjects (`platform: M4 gateway +
    M5 watch`, `lsp: ...`, `bench: ...`). No commit uses `!` or
    `BREAKING CHANGE`.

11. **Binary facts.** The debug binary is 162 MB
    (`target/debug/suspect`, 162,569,192 bytes). A release build
    (`cargo build --release -p suspect-cli`, `lto = "thin"`,
    `codegen-units = 1` from `Cargo.toml:81-83`) is 42 MB on aarch64-apple-darwin
    (42,450,752 bytes; 15.9 MB with `gzip -9`) and took 21m 27s from a cold
    target directory on a laptop shared with other builds. On macOS it
    links only system libraries (`otool -L`: CoreFoundation, CoreServices,
    libiconv, libSystem). TLS is rustls with `ring` (`cargo tree -i ring`:
    `rustls` via `reqwest` with `rustls-tls`, `crates/suspect-cli/Cargo.toml`);
    `Cargo.lock` has no `openssl-sys`, `native-tls` or `aws-lc-rs`. The C code
    is `ring`, `tree-sitter` and the vendored grammars
    (`crates/suspect-syntax/build.rs`).

12. **musl is feasible.** `cargo check -p suspect-cli --target
    x86_64-unknown-linux-musl` with `zig cc` as the C compiler finishes
    ("Finished `dev` profile ... in 46.77s", `exit=0`), so all C build scripts
    (tree-sitter, grammars, ring) compile for musl. Linking was not tested
    locally.

## Goals and non-goals

Goals:

- One tag produces every artifact: binaries, installers, checksums,
  `.vsix`, Homebrew formula, editor registry updates.
- A stable, documented asset name and checksum contract that P4's managed
  download and the GitHub Action can depend on.
- One version for the binary, the LSP `serverInfo.version`, the VS Code
  extension, the Zed extension and the rules SDK.
- A clear public crate set, with every other crate `publish = false`.
- A generated `CHANGELOG.md` that is also the GitHub release body.

Non-goals:

- Publishing crates to crates.io in the first release (see Open questions 1).
- An npm wrapper for the binary.
- Self-update (`suspect self update`). cargo-dist can add an updater later.
- Code signing and notarization for macOS and Windows. Listed under Risks.
- Linux packages (`.deb`, `.rpm`), Scoop, winget, Nix. Can be added later
  as extra publish jobs.

## Design

### Release tooling: cargo-dist

cargo-dist generates the tag workflow, builds per-target archives, writes
`.sha256` files, generates shell/PowerShell installers and the Homebrew
formula, and supports custom jobs for the editor packages. A hand-written
workflow is the alternative (see Alternatives); dist wins because the
installers and formula are the expensive part to write and keep correct.

New file `dist-workspace.toml` at the repository root:

```toml
[workspace]
members = ["cargo:."]

[dist]
# Pin the version `dist init` installs; `dist` refuses to run otherwise.
cargo-dist-version = "<pinned at init>"
ci = "github"
targets = [
  "aarch64-apple-darwin",
  "x86_64-apple-darwin",
  "x86_64-unknown-linux-gnu",
  "aarch64-unknown-linux-gnu",
  "x86_64-unknown-linux-musl",
  "aarch64-unknown-linux-musl",
  "x86_64-pc-windows-msvc",
]
installers = ["shell", "powershell", "homebrew"]
tap = "LukasParke/homebrew-tap"
formula = "suspect"
publish-jobs = ["homebrew", "./publish-editors"]
global-artifacts-jobs = ["./package-editors"]
# Zed's download_file has no xz support; see "Asset contract".
unix-archive = ".tar.gz"
windows-archive = ".zip"
checksum = "sha256"
install-path = "CARGO_HOME"
include = ["LICENSE-MIT", "LICENSE-APACHE", "THIRD-PARTY-NOTICES.md"]
pr-run-mode = "plan"
github-attestations = true

[dist.github-custom-runners]
# glibc floor = the runner's glibc (2.35 on 22.04).
x86_64-unknown-linux-gnu = "ubuntu-22.04"
aarch64-unknown-linux-gnu = "ubuntu-22.04-arm"
aarch64-unknown-linux-musl = "ubuntu-22.04-arm"
```

Per-package settings:

```toml
# crates/suspect-cli/Cargo.toml (new)
[package.metadata.dist]
dist = true

# xtask/Cargo.toml (new; it is already publish = false, this is explicit)
[package.metadata.dist]
dist = false
```

dist names the app after the package, so archives are `suspect-cli-*` and
installers `suspect-cli-installer.sh` / `.ps1`; the binary inside is
`suspect` (`[[bin]] name = "suspect"` in `crates/suspect-cli/Cargo.toml`).
The formula is named `suspect` by the `formula` key. Renaming the package to
`suspect` would make every asset `suspect-*`; see Open questions 3.

`release.yml` is generated by `dist generate` and checked in. A CI check
(`dist generate --check`, new step in `ci.yml`) fails when the config and
the workflow drift. `pr-run-mode = "plan"` runs `dist plan` on every PR, so a broken release is caught before the tag.

### Target matrix

| Target | Runner | Why |
|---|---|---|
| `aarch64-apple-darwin` | `macos-14` | primary macOS |
| `x86_64-apple-darwin` | `macos-14` (cross) | Intel Macs; Apple cross-compiles natively |
| `x86_64-unknown-linux-gnu` | `ubuntu-22.04` | glibc 2.35 floor; default for `curl \| sh` |
| `aarch64-unknown-linux-gnu` | `ubuntu-22.04-arm` | native arm runner, no cross C toolchain |
| `x86_64-unknown-linux-musl` | dist default (zigbuild) | static; Alpine, old glibc, editor download |
| `aarch64-unknown-linux-musl` | `ubuntu-22.04-arm` | static arm |
| `x86_64-pc-windows-msvc` | `windows-2022` | Windows; tier 2 until the Windows CI job is green for one release |

Not shipped: `aarch64-pc-windows-msvc` (no demand yet; add when asked),
32-bit targets. All targets use rustls with ring, so there is no OpenSSL to
link and no per-target TLS setup. The C sources compile with the target's
`cc` (or `zig cc` for musl), as the local musl check shows.

The shell installer picks the gnu build and falls back to musl when the
host glibc is older than the gnu build needs (dist behaviour). Editors always
download musl on Linux (below), because they cannot cheaply probe glibc.

### Asset contract (for P4 and the GitHub Action)

Release `v{V}` on `github.com/LukasParke/suspect` carries:

```text
suspect-cli-{TRIPLE}.tar.gz            unix targets
suspect-cli-{TRIPLE}.zip               windows target
suspect-cli-{TRIPLE}.{tar.gz|zip}.sha256
suspect-cli-installer.sh
suspect-cli-installer.ps1
suspect.rb                             (also pushed to the tap)
suspect-vscode-{V}.vsix
suspect-vscode-{V}.vsix.sha256
dist-manifest.json
source.tar.gz, source.tar.gz.sha256
```

URL: `https://github.com/LukasParke/suspect/releases/download/v{V}/{asset}`.

Rules clients rely on:

1. `{V}` is the client's own version. VS Code reads it from
   `context.extension.packageJSON.version` (`editors/vscode/src/extension.ts:38`);
   Zed uses `github_release_by_tag_name("LukasParke/suspect", "v{V}")`
   from `zed_extension_api` 0.6.0 (`wit/since_v0.6.0/github.wit:34`).
2. Platform to triple:

   | VS Code `process.platform`/`arch` | Zed `current_platform()` | Triple |
   |---|---|---|
   | `darwin`/`arm64` | `Mac`/`Aarch64` | `aarch64-apple-darwin` |
   | `darwin`/`x64` | `Mac`/`X8664` | `x86_64-apple-darwin` |
   | `linux`/`x64` | `Linux`/`X8664` | `x86_64-unknown-linux-musl` |
   | `linux`/`arm64` | `Linux`/`Aarch64` | `aarch64-unknown-linux-musl` |
   | `win32`/`x64` | `Windows`/`X8664` | `x86_64-pc-windows-msvc` |

   Anything else: no managed download; show "Locate binary…" (P4.3).
3. Archive format is `.tar.gz` (unix) or `.zip` (Windows). Zed's
   `download_file` supports only `gzip`, `gzip-tar`, `zip` and
   `uncompressed` (`zed_extension_api-0.6.0/wit/since_v0.4.0/extension.wit:19-28`);
   dist's default `.tar.xz` would not be downloadable from Zed. This is why
   `unix-archive = ".tar.gz"` is set.
4. The `.sha256` file's first whitespace-separated token is the lowercase
   hex SHA-256 of the archive. Clients ignore the rest of the line.
5. Inside the archive, the binary is `suspect` (`suspect.exe` on Windows),
   either at the root or one directory down. Clients search to depth 2
   rather than hard-coding the directory, because dist's layout is not part
   of this contract.
6. Asset names never change within a major version. A test in the release
   workflow (see Testing) asserts every name above exists.

### Editor packaging in the same workflow

New reusable workflow `.github/workflows/package-editors.yml`, called by
dist as a global artifacts job. It uploads artifacts that dist attaches to
the release.

VS Code:

```yaml
- uses: actions/setup-node@v4
  with: { node-version: 22, cache: npm, cache-dependency-path: editors/vscode/package-lock.json }
- run: npm ci && npm run compile && npm run test:headless
  working-directory: editors/vscode
- run: cargo xtask check-versions          # package.json version == tag
- run: npx vsce package --out suspect-vscode-${VERSION}.vsix
  working-directory: editors/vscode
- run: sha256sum suspect-vscode-${VERSION}.vsix > suspect-vscode-${VERSION}.vsix.sha256
```

The `.vsix` is universal: it does not bundle the binary. P4.3 downloads
the binary from the same release. Changes needed in `editors/vscode`:
`"license": "MIT OR Apache-2.0"`, `"repository"`, `"icon"` in
`package.json`; a `LICENSE` file (vsce stops with a prompt when none is
present); `.vscodeignore` excluding `src/`, `test/`, `tsconfig.json`; and
`@vscode/vsce` plus `ovsx` as pinned dev dependencies. The extension has no
bundler, so `vsce package` keeps production `node_modules`
(`vscode-languageclient`).

Zed: there is nothing to build. Zed builds extensions from source in its
registry repository (`zed-industries/extensions`), which references this
repository as a submodule with `path = "editors/zed"`. The publish job opens
a PR there that moves the submodule to the tag and sets `version = "{V}"`.
Needed first: `repository = "https://github.com/LukasParke/suspect"` in
`editors/zed/extension.toml`, licence files in `editors/zed/`, and one
manual first submission. CI already builds the extension for
`wasm32-wasip1` (`.github/workflows/platform.yml`, job `zed-extension`).

New reusable workflow `.github/workflows/publish-editors.yml` (dist publish
job, runs after the release is created, skipped for pre-release tags):

```yaml
- run: npx vsce publish --packagePath suspect-vscode-${VERSION}.vsix
  env: { VSCE_PAT: "${{ secrets.VSCE_PAT }}" }
- run: npx ovsx publish suspect-vscode-${VERSION}.vsix
  env: { OVSX_PAT: "${{ secrets.OVSX_PAT }}" }
- # open the zed-industries/extensions PR (gh CLI against a fork)
  env: { GH_TOKEN: "${{ secrets.ZED_EXTENSIONS_TOKEN }}" }
```

Secrets: `HOMEBREW_TAP_TOKEN` (dist), `VSCE_PAT`, `OVSX_PAT`,
`ZED_EXTENSIONS_TOKEN`.

### Public crate set

The crates.io-facing decision is separate from what ships in the first
release (no crates; see Open questions 1). What matters now is which crates
are kept publishable.

Foundation set (publishable, `publish` left unset):

| Crate | Why public |
|---|---|
| `suspect-source` | no internal deps; packages today |
| `suspect-syntax` | lossless CSTs; packages today (131.6 KiB compressed) |
| `suspect-low` | `LowDoc`, `NodeRef`, `Pointer`; 19 internal consumers |
| `suspect-ref` | `WorkspaceBuilder`, `Workspace`; the load path every tool uses |
| `suspect-jsonpath` | RFC 9535 over `suspect-low`; packages today |
| `suspect-oas` | typed OpenAPI views (`OpenApi`, `Operation`, `SchemaView`) |
| `suspect-overlay` | Overlay apply engine; packages today |

This set is dependency-closed (`oas` → `low`, `ref`, `source`, `syntax`;
`overlay` → `jsonpath`, `low`, `source`) and is the layer the source
proposal already calls stable ("every tool loads through
`suspect_ref::WorkspaceBuilder` + `LowDoc::parse`"). P1's `suspect-diag`
joins it when it lands, because `RefDiagnostic` (`suspect-ref`) and
`OverlayDiagnostic` (`suspect-overlay`) will be expressed in its types.

`publish = false` on the other 21 crates (16 after P8): `suspect-arazzo`,
`suspect-artifact`, `suspect-cli`, `suspect-codegen`, `suspect-config`,
`suspect-gateway`, `suspect-gen`, `suspect-ir`, `suspect-journal`,
`suspect-lint`, `suspect-lsp`, `suspect-rules`, `suspect-runtime`,
`suspect-schema`, `suspect-test`, `suspect-validate`, and (until P8 removes
them) `suspect-faker`, `suspect-reverse`, `suspect-rex`, `suspect-upgrade`,
`suspect-watch`. Reasons: their findings types change in P1
(`suspect-lint`, `suspect-validate`, `suspect-arazzo`), they are internal
models (`suspect-ir`, `suspect-runtime`, `suspect-journal`), or they are
applications (`suspect-cli`, `suspect-lsp`, `suspect-gateway`,
`suspect-codegen`). `suspect-lint` and `suspect-schema` are the next
candidates once P1 lands and `suspect-lint` no longer needs `suspect-ir`.

To keep the foundation set publishable, `suspect-ref`'s dev dependency on
`suspect-ir` becomes path-only (cargo strips unversioned dev dependencies on
publish):

```toml
# crates/suspect-ref/Cargo.toml [dev-dependencies]
-suspect-ir.workspace = true
+suspect-ir = { path = "../suspect-ir" }
```

and CI runs `cargo package` for the set (Testing).

(cargo-about reads the same licence data `cargo deny` checks) and included in
every archive.

### Versioning

One version for everything, tagged `v{V}`:

- `[workspace.package] version` and every internal entry in
  `[workspace.dependencies]`,
- `editors/vscode/package.json` (+ `package-lock.json`),
- `editors/zed/extension.toml` and `editors/zed/Cargo.toml`,
- `rules-runtime/package.json`,
- the rules SDK shim, which switches from the literal `"0.1.0"`
  (`discover.rs:110`) to `env!("CARGO_PKG_VERSION")`.

New xtask commands:

```rust
// xtask/src/main.rs (new subcommands)
/// Sets every version line listed above to `version`.
fn bump(version: &semver::Version) -> anyhow::Result<()>;
/// Fails when any version line differs from [workspace.package] version,
/// or (with --tag) from the given tag.
fn check_versions(tag: Option<&str>) -> anyhow::Result<()>;
```

`bump` edits TOML with `toml_edit` and JSON by targeted replace so
formatting is kept. `check-versions` runs in `ci.yml` and at the start of
the release workflow.

Pre-1.0 policy: a release that removes or renames a command, flag, config
key or exit code (P3's hidden aliases expiring, for example) bumps the
minor; everything else bumps the patch. After 1.0, normal SemVer on the CLI
surface, config schema and the foundation crates' APIs.

### CHANGELOG

git-cliff, config in a new `cliff.toml`:

```toml
[git]
conventional_commits = true
filter_unconventional = false
split_commits = false
commit_parsers = [
  { message = "^feat", group = "Features" },
  { message = "^fix", group = "Fixes" },
  { message = "^perf", group = "Performance" },
  { message = "^docs", group = "Documentation" },
  { message = "^(chore\\(deps|chore: bump)", skip = true },
  { message = "^(chore|ci|test|style|refactor|build)", skip = true },
  { message = ".*", group = "Other" },   # pre-convention milestone subjects
]
tag_pattern = "v[0-9].*"
```

Flow: `cargo xtask bump 0.2.0` also runs `git cliff --unreleased --tag
v0.2.0 --prepend CHANGELOG.md`; the bump PR is reviewed like any other; the
tag is pushed after it merges. dist uses the matching `CHANGELOG.md` section
as the GitHub release body. The first entry (`v0.1.0`) is a hand-written
summary, because the 216-commit history has no previous tag to diff against.

### GitHub Action

`.github/actions/suspect/action.yml` stops building from source. It gains a
`version` input (default: the action's own tag, so
`LukasParke/suspect/.github/actions/suspect@v0.2.0` runs 0.2.0) and installs
with the shell installer or by downloading `suspect-cli-{TRIPLE}.tar.gz`
and checking its `.sha256`, then runs `suspect` from `PATH`. The
`dtolnay/rust-toolchain` and `Swatinem/rust-cache` steps go.

### Docs

`README.md` "Install" becomes:

```console
curl --proto '=https' --tlsv1.2 -LsSf https://github.com/LukasParke/suspect/releases/latest/download/suspect-cli-installer.sh | sh
brew install LukasParke/tap/suspect
# Windows
powershell -ExecutionPolicy Bypass -c "irm https://github.com/LukasParke/suspect/releases/latest/download/suspect-cli-installer.ps1 | iex"
# From source
cargo install --locked --git https://github.com/LukasParke/suspect suspect-cli
```

`CONTRIBUTING.md` gains a "Releasing" section (bump PR, tag, what the
workflow does, required secrets), and its "Checks" list is replaced by
`cargo xtask ci` once P7 lands.

## Compatibility and migration

- Nothing breaks for current users; `cargo install --path` keeps working.
- The GitHub Action changes from "build in the caller's workspace" (which
  only worked inside this repository) to "download the release". Callers
  pinned to a commit before the change are unaffected.

## Alternatives considered

- **Hand-written tag workflow** (matrix build, `softprops/action-gh-release`,
  own installer scripts and formula). Full control and no extra tool, but
  we would write and maintain the shell and PowerShell installers, the glibc
  fallback and the Homebrew formula ourselves. Lost on maintenance; the
  editor jobs are custom in both designs.
- **release-plz** for versioning and changelog. It is built around
  per-crate versions and crates.io publishing, opens release PRs per crate,
  and does not know about `package.json` or `extension.toml`. Lost because
  crates.io is deferred and the editors need the same version. Worth
  revisiting for the foundation crates once they publish.
- **Platform-specific `.vsix` files with the binary inside.** No download
  step, works offline, but six `.vsix` files per release and a large
  extension download on every update. Lost because P4.3 already chose a
  managed download with checksum verification; it can be added later for
  air-gapped users.
- **glibc builds only.** Smaller matrix, but no build for Alpine and old
  distributions, and editors would need a glibc probe. Lost.
- **musl builds only on Linux.** One Linux artifact per arch. Lost on the
  allocator risk below; shipping both lets the installer prefer gnu.
- **Publishing everything to crates.io** so `cargo install suspect-cli`
  works. Needs 28 crates published in order, the `rules-runtime` files moved
  into `suspect-rules`, path-only dependencies fixed, and freezes P1-bound
  types. Lost; `cargo install --git` covers source installs.

## Risks

- **musl allocator.** musl's malloc is slow under multi-threaded load, and
  `suspect` uses rayon. The musl build may be noticeably slower than gnu on
  large specs. Mitigation: shell installer prefers gnu; measure with
  `BENCHMARKS.md`'s corpus on the rc; if the gap is large, add a global
  allocator (mimalloc) on musl targets only, as a separate change.
- **Windows behaviour.** Never tested (Problem 2-3). Mitigation: step 3
  before the first tag; Windows is labelled tier 2 in the README until one
  release has passed the smoke job.
- **Unsigned binaries.** macOS Gatekeeper quarantines downloaded binaries
  from browsers (not from `curl` or Homebrew); Windows SmartScreen warns.
  Editors download through their own HTTP clients, which do not set the
  quarantine attribute. Signing and notarization are a follow-up.
- **Secrets and third-party accounts.** Four tokens and three publisher
  accounts. A leaked `VSCE_PAT` can publish an extension. Mitigation: scope
  tokens to the one publisher, store them as environment secrets on a
  `release` environment with required reviewers.
- **dist upgrades.** dist pins its own version and regenerates
  `release.yml`; upgrades are deliberate PRs. The `--check` step stops
  silent drift.
- **Release build time.** `codegen-units = 1` with thin LTO over
  `suspect-codegen` (173,489 lines) makes each target build long
  (21m 27s locally, cold, for one target). Seven parallel runners keep wall
  time bounded; a `dist` profile with `codegen-units = 16` is an option if it
  becomes a problem.

## Open questions

1. **Which registries are in scope?** Recommended default for the first
   release: GitHub Releases (binaries, installers, checksums, `.vsix`),
   Homebrew tap `LukasParke/homebrew-tap`, VS Code Marketplace, Open VSX
   and the Zed extension registry. Not in scope: crates.io (publish the
   foundation set, plus `suspect-diag`, after P1 lands), an npm wrapper for
   the binary (the installers cover it), and npm for `@suspect/rules-sdk`
   (the binary already serves it to rules through `NODE_PATH`,
   `discover.rs:103-111`; publish it only for editor type-checking, and only
   after confirming the `@suspect` npm scope is ours).
2. **Marketplace publisher id.** `package.json` uses `"publisher":
   "suspect"`. Recommended: keep it if the id is free on both Marketplace
   and Open VSX; otherwise use `lukasparke` and change the extension id once,
   before the first publish.
3. **Rename the `suspect-cli` package to `suspect`?** It would make assets
   `suspect-{TRIPLE}.tar.gz` and allow `cargo install suspect` later.
   Recommended: no. `-p suspect-cli` appears in CI (`platform.yml`,
   `ci.yml`), `CONTRIBUTING.md` and the action, and users type `suspect`
   either way. The asset contract above stands as written. If the answer is
   yes, it must happen before the first tag, because asset names are then
   fixed for the major version.
4. **Install path.** Recommended: dist's default `CARGO_HOME`
   (`~/.cargo/bin`), the same place `cargo install` uses, so a source
   install and a binary install replace each other instead of shadowing.
5. **Attestations.** Recommended: on (`github-attestations = true`); it
   costs nothing and gives P4 a second verification option
   (`gh attestation verify`) later.
